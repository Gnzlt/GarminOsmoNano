# GarminOsmoNano: agent rules

This repo (GarminOsmoNano) holds **OsmoNano**, a Garmin Connect IQ **watch app** in Monkey C. It
controls a **DJI Osmo Nano** over the watch's own BLE: start/stop recording, take a photo, pick the
shooting mode, and show the link state, the recording state and its time.

The Nano speaks the **DUML** protocol over BLE, as documented by the open-source projects credited
in [`THIRD_PARTY_NOTICES.md`](THIRD_PARTY_NOTICES.md); the subset used here is described in the
headers of `source/duml/` and `source/camera/NanoSession.mc`. It works on a Nano at the watch's
20-byte BLE limit (field test, 2026-10-06). The Protocol menu's choices stay for other firmware, and
every frame is logged.

For anything about the Connect IQ platform, look it up in Garmin's developer docs
(<https://developer.garmin.com/connect-iq/>).

The rules shared with the other Connect IQ projects come first; OsmoNano's own follow.

## Shared Connect IQ conventions

> This section is word for word the same in GarminMotoFields, GarminOBD, GarminOsmoNano and GarminTPMS, so the
> four projects are developed one way. Change it in all four at once. `<App>` is the name the
> project section below gives for build outputs.

### Hard rules

- **Never sideload to the watch, upload to the Connect IQ Store (beta included), or publish
  anything without asking first.** Building locally is always fine.
- **The developer key never enters the repo.** It lives at
  `~/.config/connectiq/developer_key.der`, or at `$CIQ_KEY`; `*.der` and `*.pem` are gitignored.
  Every Store upload is signed with the same key, or the Store refuses it.
- No `.prg`, `.iq`, `.fit` or `bin/` output is committed. Logs and activity files off the watch
  go in the gitignored `logs/`: they hold device addresses, serials and GPS tracks.
- **Commit every step** of a change separately, once it passes the gate, and push it to `main`,
  so the history reads as the work went.
- **Every app has a Store beta**, under its own app id (`BETA_ID` in `scripts/build.sh`), and
  every version ships as both packages, release and beta, at the same version.

### Products

All four apps ship for the same watches: Garmin's **5-button round watches** (START, UP/MENU,
DOWN, BACK) with BLE for apps, **Connect IQ 5.0 or later**, 768 KB for a watch app and 128 KB for
a data field. That is 44 products: fēnix 7/7S/7X/Pro, E, 8, 8 Pro and 9, epix 2/Pro, Enduro 3,
Forerunner 165/255 Music/265/570/955/965/970, MARQ 2, D2 Mach and Instinct 3 AMOLED.
Touch-first watches (Venu, vivoactive) and monochrome screens are out.

- `scripts/devices.py` (the same file in all four) holds the candidates and checks each against
  its SDK device profile; a missing profile is reported, never assumed. To add a watch: add it to
  `CANDIDATES` in all four, `uv run --no-project python scripts/devices.py --manifest`, then
  `scripts/icons.sh`, then look at the demo on it.
- Screens are round, 218 to 466 px, AMOLED and MIP. Layouts are proportional to the screen.
  After a UI change, check the largest (454 px, fenix847mm) and the smallest (218 px, fr255sm).
- `onUpdate` only draws. Geometry, fonts, bitmaps and strings are worked out once per layout or
  settings change; never call `loadResource` or measure text per frame. In AMOLED low power
  (`System.getDisplayMode()`), draw no static bright shapes.

### Resources

- `resources/main/`: the hand-written resources (strings, settings, FIT labels, drawables), the
  base every product falls back to. `resources/main/strings/version.xml` is written by every
  build from `VERSION`.
- `resources/gen/`: generated by `scripts/icons.sh` and never edited by hand. `round-WxH/` holds
  art per screen size, `<product>/` the launcher icon at that product's size. They are
  committed, so a clone builds without the image tools.
- Connect IQ finds qualifier folders only next to the base folder, so `scripts/jungles.py` (the
  same in all four) names each product's `resources/gen/` folders in `monkey.jungle` and
  `beta.jungle`, between the generated markers.

### Build

Here (Linux, headless) the toolchain is `monkeyc` and `ciq-sim` from
`/config/workspace/tools/connectiq/`; on a Mac it is the SDK's `monkeyc`, `monkeydo` and
`connectiq`. SDK 9.2.0 or later (the fēnix 8 needs API 6.0.3). Python runs through `uv`.

```sh
scripts/build.sh            # release bin/<App>-<product>.prg for every product, and bin/<App>-test.prg
DEVICE=fenix847mm scripts/build.sh   # one product only (and the test build on it)
scripts/build.sh --demo     # also bin/<App>-demo.prg, the demo build (no BLE needed)
scripts/build.sh --iq       # also bin/<App>.iq and bin/<App>-beta.iq: always both (--beta is the same)
scripts/test.sh             # every unit test, in a fresh simulator (ciq-sim here)
scripts/icons.sh            # resources/gen/, the launcher icons, store/icon-500.png and store/hero.png
ciq-sim run bin/<App>-demo.prg fr255sm   # the demo on one device, headless
```

**The gate, for every change:**

1. `scripts/build.sh` compiles every product and the test build with strict type checking
   (`-l 3`) and **no warnings**.
2. `scripts/test.sh` passes every test.
3. After a UI change: build `--demo`, run it on fenix847mm and fr255sm, take `ciq-sim shot`
   screenshots and look at each screen.

### Test and simulator quirks

- The simulator has no BLE, so BLE code is checked on the watch; pure logic is unit tested
  behind a fake transport.
- A failed `Test.assert` shows as `ERROR` with no message in `ciq-sim test`. Bisect with smaller
  tests rather than looking for a stack trace.
- The simulator is restarted for every test run: one that still holds the app's BLE profiles
  from an earlier run crashes in `registerProfile` or hangs `monkeydo`.
- `System.println` does not reach `monkeydo` outside test runs.
- Simulator menus open as separate X windows that `ciq-sim shot` does not capture: take an
  `xwd -root` screenshot of display `:77`. Data Fields → Layout is at (217,12) → (225,37).
- Data fields: the simulator shows no data-field alerts and cannot open a data field's on-watch
  settings (`getSettingsView`). Both are checked on the watch, their logic unit tested.

### Versions and the Store

- `VERSION` holds the app version (semver: `0.x.y` for betas, `1.0.0` for the first public
  release). Bump it before every Store upload: the Store refuses a version it has seen. Add the
  version's entry to `CHANGELOG.md`, in words a user follows.
- `store/` holds everything an upload asks for, committed: `listing.md` (the form's fields and the
  upload steps), `description.txt` (the plain-text description to paste), `icon-500.png` and
  `hero.png` (rendered by `scripts/icons.sh` from their sources), and `screens/*.jpg`.
- Store screenshots come from the demo build on fenix847mm: `ciq-sim shot
  store/screens/raw/<name>.png` (raw captures are gitignored), then
  `uv run --no-project --with pillow python scripts/screens.py store/screens/raw/<name>.png
  store/screens/<n>-<name>.jpg`.
- After an upload, tag the commit: `git tag v<VERSION> && git push --tags`.

### README

`README.md` has the same shape in all four projects, so a reader finds things in the same place:

- The logo, `store/icon-500.png` at 140 px, centred; then the app's name as the title, a row of
  badges (the app type and "watches: 44", plus the licence, the Store and sponsor badges on a
  public repo), and a one-line bold tagline; then a short intro.
- These sections, in this order: **What it does**, **Supported watches** (the same paragraph,
  with the memory figure and the status line of the app), **Install**, **Using it**, **How it
  works** (a layer map of `source/` and links to `docs/`), **Diagnostics**, **Build and test**
  (the same commands), **Contributing**, **Credits**, **License**.
- Change it with the change that makes it stale. The watch list and the build commands are the
  same in all four, so they change in all four.

### Diagnostics

- **Data fields record into the activity's FIT file.** Besides the values a rider sees in Garmin
  Connect, `source/fit/Recorder.mc` writes two hidden UINT32 record fields, ids 15 and 16,
  through `source/fit/Diag.mc` (the same file in both data fields): `<x>_link` packs the live
  state (phase, ages, signal) into one number, and `<x>_counts` carries one counter per second in
  turn as `(slot << 24) | value`, the slots named in `DiagSlots`. `tools/ride_report.py` reads
  them from a ride's `.fit` (copied from `GARMIN/ACTIVITY/` into `logs/`, or exported from
  Garmin Connect). Nothing has to be set up on the watch.
- FIT limits learned the hard way: record fields cannot hold text; an array field (`:count`)
  crashes the simulator; a Monkey C Number is signed, so a packed value keeps its top bit clear;
  records exist only while the timer runs (the counters cover the whole time the field ran);
  Connect IQ fields share a small budget per activity (about 16 developer fields, reportedly
  across all data fields), so diagnostics stay in those two fields.
- **The text log is optional.** `source/Log.mc` writes `System.println` lines (with the version
  and the time) that a sideloaded app keeps in `GARMIN/APPS/LOGS/<PRG name>.TXT` only if that
  file exists. Data fields keep it behind the **Debug log** setting, off by default. The watch
  keeps about 10 KB (the file rolls to `.BAK` at 5 KB), so repeats are rate-limited.
- A watch app has no activity file: its log is the on-screen Diagnostics and the text file.

### Style

- Monkey C with explicit types on every member, parameter and return (strict type check).
- Indentation of 4 spaces. Classes are `PascalCase`; members and functions are `camelCase`, with
  a leading `_` for private members.
- Comments say *why*. Each file starts with a short header saying what it owns.
- Ad-hoc experiments go in `scratch/`, which is gitignored.

## OsmoNano

- **`<App>` is `OsmoNano`**: the app keeps that name on the watch, in the build outputs
  (`bin/OsmoNano-*.prg`) and in the log file (`OSMONANO.TXT`); the repo is GarminOsmoNano.
- App type `watch-app`, permission `BluetoothLowEnergy`. 768 KB on every product.
- **Never send a shooting-mode value outside `Nano.MODES`**: sweeping unknown values froze a Nano.
- The repo is public (MIT). `docs/` holds the maintainer's working notes and is gitignored, so
  there is no `docs/connectiq-guidelines.md` here: GarminOBD's copy is the reference.
- Pixel sizes go through `MainView.px()`. The mode art is drawn per screen size into
  `resources/gen/round-WxH/` by `scripts/mode-icons.py`; the launcher icon's master comes from
  `assets/icon-source.jpg` (`scripts/icons.py`).
- In the simulator on fenix847mm, the buttons are at fixed window positions: hold UP (30,445) for
  the menu, DOWN (55,605), START (685,300). The real app stays on "Choose camera", with an empty
  list. The demo build walks every screen in a 60-second loop.
- Diagnostics: the **Diagnostics** screen (menu) shows the frame log live; `source/Log.mc` also
  writes every line to `OSMONANO.TXT` when that file exists on a sideloaded install.
  `source/RunTrail.mc` keeps one record in Storage per run (clean stop or not, uptime, peak and
  least-free memory, link phase), so the next launch logs how the last one ended: a watch app has
  no FIT file for this, and a Store or beta install writes no text log. Writes to Storage go
  through `Store` (`source/Store.mc`), which cannot throw: an exception in a BLE callback ends the
  app.

### BLE and DUML rules

These come from the Nano's behaviour, as recorded by KonradIT. Breaking one fails on the camera, not
in the compiler.

- **One GATT operation in flight;** writes are split into 20-byte chunks (the Connect IQ maximum).
- **The GATT setup has three steps:** the CCCDs of both `FFF4` and `FFF5`, then `01 00` written to
  the `FFF4` value with response, then about 200 ms of settling. Without them, the camera ACKs
  writes at the ATT level and answers nothing.
- **Frames are at least 120 ms apart.** `FFF5` is write-without-response, and back-to-back writes
  are dropped. Answers to the camera's requests go ahead of the queue.
- **Answer every camera request** (flags `0x40`) once: flags `0xC0`, same seq, source and
  destination swapped. Unanswered, the camera drops the link.
- **A keepalive every second,** or the Nano drops the link after 5–6 s.
- **Notifications arrive cut to 20 bytes:** frames longer than that are delivered as partial (the
  header is checked, the payload is what arrived). A decoder returns null for a field whose bytes
  did not arrive. Never guess.
- **Recording state comes only from the camera's status** (push or `02/70` poll), never from a
  command's reply. It is read only from the full status form (37+ bytes) in video work mode
  (`flags & 0xC0`); the compact form's bit `0x40` is the dock.
  `0x02/0x02` is not a toggle.
